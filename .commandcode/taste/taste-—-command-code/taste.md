# Taste — Command Code
- Writes requests in Vietnamese and expects replies (explanations, step lists, inline comments) in Vietnamese. Confidence: 0.7
- Prefers remediation batched by severity: fix the critical/high-severity set first rather than mixing low-severity cleanups into the same pass, then do a review/verification pass over the changes afterward. Confidence: 0.65
- Drives long remediation efforts with terse proceed-with-next-tier instructions (e.g. "continue to High", "continue on Medium/Low") rather than per-item sign-off, so each tier should be carried to completion and self-verified before reporting back. Confidence: 0.7
- Relies on the agent ending each pass with an explicit "remaining items" list of deferred lower-severity work, since subsequent instructions simply reference that list ("continue on Medium/Low", "start doing the remaining items") rather than restating scope. Confidence: 0.65
- When handed a deferred backlog, expects the whole list to be implemented end-to-end without asking which subset to do first or seeking per-item approval. Confidence: 0.6
- Expects terse git instructions ("commit changes and push", sometimes just a bare "push") to be carried out end-to-end — stage, write a summary commit message, and push straight to the current branch — without asking for confirmation, branch choice, or PR flow. Confidence: 0.7
- Wants commits scoped to the actual change: stage only the source files that implement the fix and leave tooling/local config (e.g. `.commandcode/`) out of the commit, then report the new commit hash and where it landed. Confidence: 0.5
- Terse environment/test requests ("tạo venv và chạy test") mean "get to a green test suite": expects the agent to set up the venv, install deps, provision whatever external services the tests need (e.g. spin up a temporary Docker Postgres/pgvector container) without asking permission, and then tear those ad-hoc resources down afterwards. Confidence: 0.6
- Treats production infrastructure/data work as the same kind of terse one-line handoff ("đã gắn DATABASE_URL production vào .env, chạy migrate lên giúp tôi", "seed admin cho production"): expects it carried out in a single pass — verify config, inspect current state, enable any required extensions, apply, then verify the result — without a plan or approval gate even though a live production DB is being mutated. Confidence: 0.65
- Leaves operational details (credentials, naming, emails, passwords) unspecified in the request and expects the agent to pick sensible, idempotent defaults itself and report exactly what it created afterwards, rather than asking clarifying questions first. Confidence: 0.5
- Keeps secrets/settings in the project's `.env` and expects the agent to read them from there itself rather than having values pasted into the conversation. Confidence: 0.5
- Wants a failing test triaged to an actual root cause before being changed — reproduce the failure in isolation, confirm the contract against the real client/consumer, and fix the test rather than loosening the API — then re-run the whole suite and report pass counts. Confidence: 0.55
- Wants failure paths to leave no orphaned side effects: a partial operation that uploads/creates a remote asset must delete it again if any later step fails, and expects such cleanup wired into every error branch of the flow rather than only the happy-path error handler. Confidence: 0.55
- Reports runtime bugs by pasting the raw artifact with little or no accompanying question — either the verbatim user-facing error string (often Vietnamese UI copy, no stack trace), an unedited dump of server/console log lines, or a full Python stack trace plus a bare "debug this" — sometimes prefixed by a single terse Vietnamese sentence stating the desired behaviour (e.g. "Tôi muốn khi gặp lỗi về upload cloudinary thì xoá file đã upload lên." + server log), which is expected to be tied to the pasted output and implemented without further spec questions — and expects the agent to locate where that output comes from, identify what it hides, reproduce the failure locally, and pin the real root cause instead of patching the message or guessing. A follow-up message that supplies the missing detail arrives the same way ("Cụ thể lỗi như sau:" + the full traceback), not as prose. Confidence: 0.85
- Sometimes the paste is a pure diagnosis ask ("Lỗi này là gì?" + a third-party API stack trace such as a Gemini 400 FAILED_PRECONDITION) and expects an explanation-only answer: the error code's documented meaning, the culprit traced into their own config/deployment (serverless region, missing billing, provider switch) rather than blamed on application code, a short ranked list of concrete remedies, and sources — without unrequested edits to the codebase. Confidence: 0.55
- The verb on a pasted error signals what is wanted: "Lỗi này là gì?" gets an explanation only, while "Xử lý lỗi này:" + traceback is a request to actually change the code — and the fix is expected to be consistent with what the rest of the system already supports (check the upload UI/validation, other supported formats, and docs before adding or rejecting a case), not a one-line patch at the raise site that just silences the message. Confidence: 0.55
- Fires off several pasted errors back-to-back ("Còn lỗi này thì sao?", "Vậy lỗi này tới từ đâu?", "lỗi này là sao?") without waiting for the previous one to be fixed, and expects each to be diagnosed on its own terms while noticing that they share a cause (e.g. all traces of provider/region rejections through the same client) instead of treating them as unrelated tickets. Confidence: 0.55
- For config-driven failures (wrong model name, bad key, invalid setting), expects the root cause traced all the way to the offending value in `.env`/settings and validated against the real external API before the edit is made — not a guess-and-edit. Confidence: 0.5
- Reports regressions by anchoring them to a git event ("Từ trước commit Clean up project ... hoạt động tốt, nhưng tại sao sau đó các thay đổi lại khiến nó hỏng") and expects the breakage traced back through the commit history — diff the cleanup/refactor commit(s), name the specific change that removed or altered the working behaviour, and restore it — rather than re-fixing the current symptom from scratch. Confidence: 0.6
- Pushes back with what they believe their config says ("Vercel tôi đang set là dùng openai mà nhỉ") and expects the discrepancy reconciled by inspecting the effective runtime configuration — deployed/Vercel env vars vs `.env` on disk vs the client actually imported at the failing line — to explain why the running code hit a different provider/setting than intended, instead of restating the diagnosis. Confidence: 0.6
- Often takes the edit into their own hands once the diagnosis is concrete ("okay i will fix it myself"), so debugging should end with a pinpointed culprit (file/line, exact wrong value, exact replacement) plus any post-edit step needed, rather than a lecture or unrequested code changes. Confidence: 0.5
- Follows up earlier reported bugs with a terse status check (e.g. "Lỗi AI sinh không đúng json array đã sửa chưa?") and expects a direct answer plus the outstanding fix actually applied in that same turn — not another diagnosis-only report, and not a "done" summary from a previous pass that left the reported symptom untouched. Confidence: 0.55
- Sends feature requests as a single terse Vietnamese sentence naming only the capability ("Thêm tính năng cập nhật thông tin cá nhân và đổi mật khẩu.") and expects a complete vertical slice in one pass — serializers/views/URL routes, the page template + JS, wiring into existing navigation/cache, and new tests — plus verification (framework check, targeted then full test suite, JS syntax, page render) before reporting a short bullet summary of what was added. Confidence: 0.6
- Does not spec out scope details of a feature (e.g. whether the avatar is a URL field or a direct Cloudinary upload); expects the agent to implement the reasonable minimal option itself, deliver it working, and flag the unimplemented alternative at the end instead of blocking on a clarifying question. Confidence: 0.55
- Config-change asks are just as terse as feature asks and may arrive in English ("Help me change ai model in env from 4o-mini to gpt 6 luna"): the value is named loosely and the location left unspecified, so the agent should locate the setting itself and resolve the canonical third-party identifier (e.g. the exact API model ID) before writing it into `.env`, then edit the variable in place (and mirror it in `.env.example` where relevant) rather than editing code. Confidence: 0.5
- Reports "broken" environment/dev-experience symptoms in one bare Vietnamese line with no details at all (e.g. "Tại sao tôi không chạy local được >") and expects the agent to start the app itself, probe the actual endpoints/status codes to observe the misbehaviour, confirm the cause by toggling the suspected setting, and then explain it with a concrete fix — not speculate. Confidence: 0.55
